# 程序判定与汇总规则 v1

此文件是待实现的规则说明，不是已经运行的评分程序。技术成功率和所有汇总计算不使用大模型。

## 一、数据分流

每条保留sample_id、run_id、bot_id、category、attempt、题库/资料/系统配置版本和context_stage。每个机器人预定40道知识库内、5道知识库外、5道模糊题。重试不得覆盖初次记录或冒充新题。

分开记录：

- technical_status：技术链路状态。
- context_capture_status：完整、确认空、缺失、不完整、关联不确定。
- answer_status：业务回复、纯故障兜底、空/缺失。
- metric_status：scored、not_measurable、not_applicable、needs_review、scoring_error。

技术调用失败不自动等于“没有采集到context”：可完整记录失败或空返回。反之，缺少采集记录不能推断检索为空。

## 二、模型输出校验

- 仅接受可解析JSON和规定字段类型。整数0/1或0～4不能用true/false代替。
- ID、事实原文、声明数量与输入对应；召回模板逐字引用须能在对应context找到。
- 出现遗漏、多余项、越界值、非法引用或空理由时，保存原响应并记评分失败，有限重试使用相同评分版本。
- 裁判失败不得默认为机器人0分；不得从任意数字或拒答关键词猜分。
- 自动裁判分与人工修订分分开保存，人工审核状态必须有实际审核记录才能置完成。

## 三、六项汇总

1. 固定必要事实召回：每题sum(verdict)/事实数，再对有效题取算术平均。空事实列表属于标准数据错误。存在未决事实时整题待复核，不缩小事实分母。列可测题数/40及缺失原因。
2. benchmark正确性：sum(score)/有效评分题数，再除以4得到标准化分数。空/缺失回答不伪造输入；另列无有效答案数。有实际故障文本时可由原裁判评分，但不覆盖技术失败。列有效评分题数/40；不是通过题数/40。
3. RAGAS忠实度：每题支持声明数/全部声明数，再取有效题平均。空声明为NaN/不适用，缺context不可测，纯故障回复按项目纳入规则排除。均单列数量，不能当100%。
4. 知识库外：人工确认通过题数/预定5题。失败、空回复和故障兜底仍保留在分母；待复核不能当作通过，未全部审完只能发布暂定结果。
5. 模糊题：同上，人工确认通过题数/预定5题。
6. 技术成功：证据充分且在冻结截止时间内完成的成功题数/预定50题。证据不足时只报告已确认成功数和未知数，不能称全量技术验收完成。

所有平均分无有效样本时返回null/未测，不能返回0或100%。四个机器人分别汇总，不把200条混成一个成绩。

## 四、端到端技术成功的逐题规则

运行前固定deadline_ms以及每条链路需要完成哪些调用。满足以下所有条件才记confirmed_success：

1. 对应题目确实发送，并有可关联的起始时间。
2. 本轮按其链路要求需要的调用最终成功；允许中途失败后重试恢复，但保留错误和重试次数。不能规定机器人1也必须有MCP。
3. 最终不是空回复、处理中提示或纯故障兜底。正常业务拒答/澄清可以技术成功，内容是否合格另评。
4. 有最终回复送达证据，且时间在截止内。SDK发送回执和客户端显示是不同证据层级，按冻结的收件定义判断。

确认未恢复的调用失败、未送达或超时记confirmed_failure；只有缺少日志、未知完成时间等情况记insufficient_evidence，不凭无记录猜失败原因。

界面轮询看到回复的时间只是观察上界。若完整回复在截止前已被看到，可证明这一收件时间条件满足；截止后才看到不能据此证明实际超时。不得把QA内部耗时当成完整端到端耗时。

## 五、评分版本清单

每轮冻结：标准题库hash、required_facts审核版本、资料版本、被测配置、裁判模型完整ID/供应商、模型参数、提示词hash、RAGAS及相关依赖版本、重试上限、context阶段和纳入规则。

模板包中的裁判模型和采样参数尚未选定。温度可优先设为供应商支持的0，但温度0不代表绝对确定性；不支持的参数不能强传。正式评分前用少量样例校准并冻结。

切分版与全文版不能混算；保留历史与逐题隔离的会话条件分别标注。context来自proxy_response与model_input_context时分别标注，未经验证不得称为完全同口径比较。
